**Philosophy:** Lightweight, pragmatic, highly secure, and optimized for Manga, Comics & Literature.

Narrow `seal_series_locks` scope — held on the automatic path, deliberately left open on the two manual paths (v1.7.0):** the automatic re-lock after a soft fail (`NEEDS_RELOCK`) now passes `lock_keys` derived from the payload it actually wrote (`kavita_api.lock_keys_from_payload`), so it no longer freezes the publisher that came from your files, a Kavita+ value or a field left open on purpose. `formatLocked` disappeared with the field itself — `UpdateSeriesDto` has never carried `Format` / `FormatLocked`, in any Kavita version. ### 🧊 Parked (no active work)
- [ ] **Global pacing net for third-party scrapers — decided against, not missing:** BF148 fixed pacing inside the core scrapers, per request. A community scraper that does its own HTTP calls without going through the helper can still burst, and the obvious guard would be a global net (a pacing gate around every outgoing request, whoever issues it). **Deliberate decision: no global net.** It would add a chokepoint on every request for a class of scraper the project does not ship, hide the offending scraper instead of exposing it, and interact badly with the per-provider pacing that already works. The line held is: fix the scrapers that ship, and treat a third-party burst as that scraper's bug.
- [ ] **C29 follow-up. Event-pause worker — parked / superseded:** Original QoS idea (emit candidates over WebSockets, block the worker on `eventlet.event.Event` until pick/skip). **C29 Manual Review** already parks series as `PENDING_REVIEW` and lets the batch continue; the user reviews asynchronously. **C63** durable batch queue covers pause / resume / restart. A synchronous Event-pause path would freeze large batches on every ambiguous match and duplicate that UX — not worth a second mode.
- [ ] **C8. Resiliency & exponential 429 backoff — parked:** Per-provider `throttle_provider` / **C34** already spaces calls by each scraper’s `rate_limit` (idle = no wait). No field reports of systemic 429s on large batches when staying under those delays; Open Library already has a simple 429 pause. Full exponential-backoff machinery deferred unless real bans appear. Optional later: light `Retry-After` / single retry — not a product priority. **Update v1.7.0:** a real ban did happen (Bédéthèque, during the audit campaign), and the cause was not a missing backoff but the pace being applied once per `fetch()` instead of per request — see BF148. `Retry-After` is now read and logged by `log_provider_http_error`. Stays parked: with the pace correctly applied, there is still no evidence that backoff machinery would prevent anything.
